# 竞品分析：圆周旅迹 Pi Travel（pitravel.cn）

> 研究方式：使用浏览器自动化工具实际打开并操作 https://www.pitravel.cn/plan?lang=en-US ，包括点击交互、DOM/控制台/网络请求检查、移动端视口模拟（375×812）。未注册账号、未输入任何手机号/验证码等个人信息（登录墙背后的功能仅通过公开文案/可见交互推断，已在文中明确标注"未实测"）。
> 研究日期：2026-08-13

---

## 1. 网站概览

**产品名称**：圆周旅迹 / Pi Travel（官网 pitravel.cn，slogan："时间、自由和有用的经验"）

**产品定位**：一款专注"行程规划"的中文旅行工具，核心卖点是"1分钟创建行程，或帮你一键解析"——即两条创建路径：
1. **AI 对话式生成**：用一句话描述旅行想法（目的地、人数、偏好），AI 直接生成一份可编辑的逐日行程。
2. **链接/文本解析**：粘贴小红书笔记、微信公众号文章、苹果地图指南（Apple Maps Guide）链接、口令码或纯文本，自动抓取其中提到的地点，一键转成收藏点位或整份行程副本。

**目标用户**：从首页编辑部内容（"亲子出行舟山·东极岛3天2夜"、"杭州龙坞一日游"、"上海咖啡馆 Citywalk"等）和产品博客文案判断，目标用户是**在小红书/微博上被种草、习惯"抱佛脚式"临时规划旅行的年轻/亲子出行人群**，主打自由行、Citywalk、亲子游等场景，官方在博客里反复强调"全部功能免费"。

**核心功能支柱**（与"旅记"对比的关键维度）：
- 行程规划（逐日清单 + 地图 + 附近推荐点位）
- 内容聚合（小红书/公众号攻略一键转行程）
- 编辑部精选行程模板 + 主题收藏夹（"地点合集"）
- 多人协作编辑（官方博客声称"支持多人实时协作编辑"，**登录墙内功能，未实测**）
- 全平台覆盖：网页版（pitravel.cn）、iOS/安卓 App、Chrome 浏览器插件（"一键导入攻略链接"）

**明显缺失的支柱**：全站没有发现任何"预算/花费/记账/分账/汇率"相关功能入口或文案（对首页、Explore 页、行程详情页做了全文关键词扫描，`预算` `花费` `记账` `分账` `汇率` 均为 0 命中）。这与"旅记"的"行程记录 + 旅行财务记录"双支柱定位形成明显差异，详见第 5 节。

## 3. 优点分析（值得"旅记"借鉴）

### 3.1 时间轴里直接嵌入"站点间通勤时间"——不用切到地图就知道好不好走
pitravel 在逐日列表的每一项下方直接印出"到下一站的距离+时间"（如"1.1千米 14分钟"），而不是要点开地图才能看路线是否合理。这是一个**零额外点击成本**的信息设计：用户扫一眼列表就能判断行程是否太赶、是否需要挪动顺序。
**为什么值得学**："旅记"目前的时间轴视图（如果只列出活动本身）可以直接在两个相邻行程卡片之间插入一行"步行/驾车 X 分钟 · X 公里"的细线提示，成本很低（只需一次静态距离计算或调用地图 API 的 directions 接口），但对"这一天安排是否合理"的判断力提升很大，尤其对不熟悉当地地理的马来西亚华人家庭用户（去中国/日本/欧洲旅行时最怕"两个景点看着近，实际要转两趟车"）。

### 3.2 "待计划"侧边栏：把"附近还有什么好玩的"直接摆在编辑器里
详情页右下角"总览/推荐/待计划/收藏"四个Tab里的"待计划"，会按类别（游玩/吃喝/购物/住宿/其他）把AI或编辑推荐的周边点位列出来，且带具体数量（游玩·24、购物·2...），用户可以直接从这个候选池里挑选拖入某一天，而不需要跳出编辑器去搜索地点、复制地址再粘贴回来。
**为什么值得学**：这是把"发现"和"编辑"合并到同一个界面的做法，减少了"规划行程"这件事里最耗时的环节——找地点。"旅记"如果未来要做"AI推荐附近景点"或"根据当前行程自动补全空档"，可以直接参考这种"编辑器里长期驻留一个可分类筛选的候选点位面板"的交互，而不是做成一个独立的"搜索"弹窗。

### 3.3 内容解析（"解析"Tab）：把小红书/公众号攻略"一键转成行程"
这是 pitravel 差异化最大的功能：用户粘贴一条小红书笔记链接、公众号文章链接，甚至苹果地图指南链接，系统自动抓取里面提到的地点，转成可编辑的行程或收藏夹。产品博客里反复拿这个功能做内容营销（"找到旅行搭子但不想做计划？直接把攻略链接甩进去"）。
**为什么值得学**：用户的记忆库里已经记录了"旅记"有"小红书招募测试用户策略"，说明目标用户（马来西亚华语家庭）本身就高度依赖小红书获取旅行灵感。如果"旅记"未来要做"从种草到规划"的转化路径，"粘贴小红书链接自动解析地点"会是一个很有说服力的获客钩子——哪怕第一版只支持"识别文本中的地名并逐个搜索地图坐标"这种轻量实现，也比完全没有这个功能强。**但要注意**：这需要处理小红书反爬、内容版权/合规风险，属于中长期、高投入功能，不建议短期内投入。

### 3.4 主题化"地点合集"（Place Collections）——比单条行程更轻量的内容单元
Explore 页的"地点合集"（如"中国登山健身步道33条""上海自拍馆图鉴""《破云》四城圣地巡礼"）是介于"完整行程"和"单个收藏点"之间的一种内容形态：一组主题点位，可以整体"一键订阅"加入自己的收藏，再自由决定怎么排进行程。
**为什么值得学**：不是所有灵感都能一次性变成"某天几点去哪"的完整行程,很多时候用户只是想收藏"曼谷好吃的甜品店清单"这种松散的点位集合。"旅记"如果只有"行程"这一种数据结构，可能会逼着用户把还没想好日期的灵感硬塞进某一天。可以考虑增加一种更轻的"心愿单/收藏夹"实体（不绑定天数），行程创建时可以从收藏夹里批量拖入——这也顺便解决了"旅记"用户常见的"看到小红书推荐但还没定具体哪天去"的过渡态。

### 3.5 精选模板 + "复制为我的行程"，降低新用户的第一次创建门槛
首页和 Explore 页大量展示编辑部制作的高质量行程模板（含真实点位、走心的一句话点评、图片），用户可以直接"复制为我的行程"再自行修改，而不是从空白页开始规划。
**为什么值得学**：对"旅记"这种主打"家庭出行"的产品，可以做一批"3天2夜家庭亲子游模板""长辈友好行程模板"，降低第一次使用时"不知道从哪开始建行程"的门槛，尤其对不熟悉产品操作、习惯"抱佛脚"的家庭用户很友好。

### 3.6 单页面内完成"多日全览 + 拖拽调整"，不强制切换视图才能看全局
pitravel 的详情页把 DAY 1/2/3 all-in-one 地垫叠在一个可滚动列表里，配合右侧地图和底部推荐面板，用户不需要在"某一天详情"和"全程概览"之间来回切换视图,一屏就能看到整个行程结构，并且允许拖拽调整地图/推荐面板的宽高比例来适应自己的操作习惯。
**为什么值得学**：如果"旅记"的时间轴视图目前是"选中某一天才能看到当天详情"的模式，可以评估增加一种"全程连续滚动"的浏览方式（哪怕只是只读浏览模式），方便用户做"整体行程节奏检查"，例如判断"是不是第2天排太满、第4天太空"。

## 4. 缺点/短板分析（"旅记"应该避免踩的坑）

### 4.1 几乎所有核心写操作都被登录墙拦住，且没有访客试用
点"新建计划"、在AI输入框里打字提交、点"复制为我的行程"——只要是任何"创建/保存"类操作，立刻弹出手机号+验证码或微信扫码的登录弹窗，**没有任何"先创建再登录保存"的访客模式**。用户在还没体验到产品价值之前就被要求提供手机号，转化路径非常陡峭。
**旅记应避免**：既然"旅记"已经是 Dexie(IndexedDB) 本地优先架构,应该坚持"先在本地免登录把行程建起来、体验完整功能，需要跨设备同步/家庭协作时才引导登录"的路径,这本身就是相对 pitravel 的结构性优势,不要在后续版本里为了"数据看板"之类的运营需求而提前收紧免登录能力。

### 4.2 登录弹窗关闭按钮有真实的前端 Bug，会冻结整页交互
如第2节所记录，点击登录弹窗的关闭按钮后，一个不可见的全屏遮罩会卡在动画中间状态，导致整页失去响应,必须刷新才能恢复。这是一个通过CSS class检查直接复现确认的真实缺陷，说明其弹窗/遮罩的过渡动画状态管理（大概率是 Vue `<Transition>` 的 enter/leave class 处理）在某些时序下会出错。
**旅记应避免**：如果"旅记"的登录弹窗、任何 Modal/Sheet 组件用了类似的进出场动画，务必在关闭时用一个明确的、幂等的状态机（例如一个单一的 `isOpen` 布尔值配合 `v-if`/条件渲染完全卸载 DOM，而不是靠一堆过渡 class 叠加来猜测当前状态），并针对"打开→立刻关闭""重复点击关闭"等边界情况做手动测试。

### 4.3 移动端网页体验被有意阉割，逼用户下载 App
在手机浏览器宽度下打开任意行程详情页，会先弹出"此链接需要在电脑上访问"的拦截层,即便选择"继续到手机端"，进入的是功能残缺的简化H5页——"待计划"的具体内容被隐藏，提示"Open the App to view"。核心的拖拽编辑、地图双栏布局等完全没有移动端网页适配，只有 App 才是"完整版"。
**旅记应避免/应保持优势**：这是"旅记"作为**离线优先PWA**的核心差异化机会——马来西亚家庭出行大多用手机规划和查看行程,如果"旅记"能在手机浏览器（包括弱网/无网环境）上提供和桌面端同等完整的核心体验(而不是导流去下载原生App),这本身就是相对pitravel的结构性胜势,后续任何新功能都应该先保证移动端网页可用,再考虑要不要加桌面端专属的高级操作(比如更复杂的拖拽)。

### 4.4 "?lang=en-US" 参数形同摆设，国际化是半成品
URL 里挂 `?lang=en-US` 完全不会让主站切换成英文，只有移动端简化 H5 分享页里出现了**中英文混杂、语法不规范**的过渡态翻译（"375meter·5minute"缺空格、单复数错误；"待计划 Open the App to view"中英文直接拼接在一行）。这说明 pitravel 目前只把国际化做到了"分享页粗糙翻译"的程度,产品主体依然是纯中文单一市场产品。
**旅记应避免**：马来西亚是英语/华语/马来语三语环境,如果"旅记"要做多语言支持,应该从设计阶段就把 i18n 当作一等公民(统一的文案key、单位/数字/日期的本地化格式化,而不是后期在个别页面手工拼接翻译字符串),避免出现pitravel这种"看起来支持多语言、实际上只做了一半"的尴尬状态。

### 4.5 首页"我的计划"卡片是视觉欺骗性的静态占位图
未登录/无行程时,首页展示的三张"行程卡片"(如"四月是属于杭州龙坞的！")在视觉上和真实的"我的行程"卡片完全一样(标题、天数、地点数、编辑者头像、编辑时间),但实际是硬编码的 `empty-journey-card` 空状态占位图,点击没有任何反应。这种"看起来像内容、点了没反应"的设计会让新用户困惑,以为遇到了故障。
**旅记应避免**：空状态设计应该在视觉上明确区分"这是示例/引导性内容"和"这是你真实的数据",比如加上"示例"标签、置灰处理、或点击后明确跳转到"新建向导"而不是完全无响应。

### 4.6 没有实际的时间调度能力，只有相对的"Day N"顺序
经全文正则扫描确认,pitravel的行程里没有任何具体时钟时间(如"09:00")、也没有绑定真实日历日期(如"2026年5月1日")——每一天只是一个有序列表,不能标注"几点到几点"、不能感知"这天是周末还是工作日、会不会撞上目的地的公共假期"。
**旅记应保持优势**：这正是"旅记""时间轴/日历视图切换"这个已完成功能相对pitravel的直接胜势——已经支持真实时间和日历视图,不需要额外开发,只需要在对外宣传/竞品对比时明确强调这一点。

### 4.7 完全没有行程内的花费记录能力
如第1、2节反复确认,pitravel在行程规划的全流程里没有任何"预算""花费""记账""分账""汇率"相关功能。旅行中"这顿饭花了多少""这次门票谁先垫付的"这类高频需求,pitravel完全没有覆盖,用户如果想记账只能跳到别的App(如splitwise类工具)。
**旅记应保持并放大优势**：这是"旅记"两大支柱之一(汇率簿、预算、AI拆账结算)相对pitravel的**结构性差异化**,建议在任何对外传播("为什么选旅记而不是别的行程规划App")中把"行程规划+旅行账本一体化,不用在两个App之间来回切"作为核心卖点之一。

## 6. 具体可执行的改进建议清单（按优先级排序）

### 高优先级（低成本、高确定性收益，建议下一个迭代周期内评估落地）
1. **在时间轴/日历视图的相邻活动卡片之间插入"通勤时间提示"**（如"步行12分钟 · 900米"）。参考 pitravel 的做法：只需一次距离/时长计算（可用已集成的地图服务的 Directions/Distance Matrix 能力，或先做简单的直线距离+步速估算作为MVP），UI 上做成一行细字即可，不需要额外的交互面板。
2. **给"旅记"的空状态（无行程/无预算记录时）设计明确的视觉区分**（如虚化底色、"示例"角标、点击后跳转创建向导），避免用户像在pitravel上一样把示例内容误认为可交互的真实数据。
3. **梳理并修复类似"动画状态卡死导致全屏拦截点击"的隐患**：审查"旅记"里所有 Modal/弹层组件的开关逻辑，确保关闭动作是幂等、单一状态源驱动的，不依赖多个CSS过渡class叠加判断是否已关闭；建立"打开→立即关闭→重复点击关闭按钮"的手动测试清单项。
4. **在对外物料（落地页/应用商店介绍/小红书招募文案）中明确对比强调"旅记"已领先的四点**：(a) 行程+账本一体化、无需在两个App间切换；(b) 完全离线优先的PWA，手机浏览器上体验和原生App对等；(c) 时间轴+日历双视图，支持真实时间和日期，而非只有"Day N"顺序；(d) 邮箱magic-link登录，不依赖中国大陆手机号/微信，更适合海外华人家庭。
5. **【新增，登录后实测发现】审查"旅记"任何分享/可见性功能，确保"打开分享面板"这个动作本身绝不会静默改变数据可见性**：pitravel 实测证实，仅仅点开"分享"弹窗（不点任何"设为公开"按钮）就会把行程可见性从"仅自己可见"自动切换成"获得链接者可见"，这是一个真实的隐私默认值陷阱。"旅记"若做类似功能，"生成/复制分享链接"和"实际放宽访问权限"必须是两个需要用户分别确认的步骤。

### 中优先级（需要一定开发投入，建议列入下一到两个季度的路线图讨论）
6. **评估增加一种"不绑定具体天数"的收藏夹/心愿单实体**，参考 pitravel 的"地点合集"以及登录后实测确认存在的"收藏到收藏夹"独立入口（见7.5节）：用户可以先把小红书/朋友推荐的地点/餐厅收藏进一个主题清单,等确定行程日期后再批量拖入某一天,缓解"有灵感但还没定行程"的过渡态。
7. **制作官方精选行程模板**（如"3天2夜家庭亲子游""长辈友好慢节奏游"），提供"复制为我的行程"入口,降低新用户第一次建行程的门槛,尤其是对操作不熟悉的中老年家庭成员友好。
8. **评估"附近推荐点位"发现式加点面板**：在行程编辑器里长期驻留一个可按类别筛选(景点/美食/购物等)的"附近还有什么"侯选列表,而不是让用户跳出编辑器单独搜索、再手动加回来。
9. **内部核实并明确"旅记"当前的多人协作编辑能力现状**：pitravel 拿"多人实时协作编辑"作为核心卖点之一，且登录后实测确认其后端确实有"按编辑者记录变更"的版本历史基础设施（见7.6节），并非纯营销话术。如果"旅记"的家庭多成员协作还停留在"各自记录、事后合并"的阶段，建议评估是否需要做成实时同步编辑（尤其考虑到"旅记"本身就是household隔离架构，天然适合做成"全家一起在线改行程"的场景），同时可以顺带补上"自动保存+可回滚版本历史+变更归属"这个安全网。
10. **评估"AI生成分享图片"功能**（见7.3节）：把行程一次性渲染成适合发小红书/朋友圈的信息图（"路线手帐版"/"攻略卡片版"两种风格），对"旅记"正在推进的小红书获客策略而言，可能比纯文字/表格导出更有传播力。
11. **评估单日"一键优化路线"功能**（见7.6节）：对多地点的一天自动重新排序，减少手动拖拽调整的负担。

### 中优先级（续，第8节完整案例新增）
11.5. **评估AI一句话/一键生成完整行程的能力**：第8节的南京6天真实案例证明这条路径能生成"每日主题名+每个地点的实用介绍文案+距离耗时"的完整内容，体验上明显超越"只给一个空白编辑器"。这是一个大投入项（需要接入LLM+可靠的地点/POI数据），但如果"旅记"要进一步降低新用户首次建行程的门槛，可以作为比第6节第7点"预制模板"更进一步的方案来评估，两者也可以配合（模板覆盖不到的目的地，用AI兜底）。
11.6. **AI/推荐生成逻辑必须主动过滤"已关闭/暂停营业"的地点，不能只在文案上标注**：第8.4节实测发现，pitravel的AI生成结果里出现了4个明确标注"暂停开放/暂停营业"的地点，数据本身是对的，但没有在生成阶段被过滤掉。"旅记"如果做类似的AI生成或"附近推荐"功能，接入的地点数据只要带停业/关闭状态字段，生成逻辑必须显式排除，这是一个容易被忽视的工程检查项。
11.7. **候选推荐池要排除已经加入行程的地点**：第8.5节实测发现"老门东"已经被排进正式行程，但仍出现在"待计划"推荐池里。"旅记"如果做类似的"附近推荐/候选点位池"功能（见第6节第8点），过滤逻辑要包含"排除本行程内所有天已用过的地点"。

### 低优先级/观察项（高投入或高风险，暂不建议投入，但保持关注）
12. **"粘贴小红书/公众号链接自动解析成行程"功能**：内容营销价值很高、也高度契合"旅记"目标用户(马来西亚华语家庭习惯刷小红书找灵感)的使用习惯,但涉及第三方内容抓取的合规/反爬风险和较重的NLP/LLM地点抽取工程投入,建议列为观察项,等核心两大支柱(行程+账本)进一步打磨稳定后再评估投入。
13. **多语言(EN/ZH/MY)国际化**：如果"旅记"未来要拓展到马来语或英语为主的家庭用户,务必从i18n框架设计阶段就统一处理,避免重复pitravel"lang参数摆设、分享页机翻中英混杂"的半成品状态；这是一个需要提前规划而非后期补丁的架构决策，建议尽早在技术选型层面(文案key结构、日期/数字本地化)预留空间，即使暂不实现完整翻译。

## 7. 登录后深入实测补充（2026-08-13 第二轮，用户本人登录后由我继续操作）

> 用户在 Browser 面板里用自己的账号完成登录（我未接触手机号/验证码/密码），登录后我用该已登录会话继续点击测试，创建了一个真实的"北京市旅游"测试行程用于探索编辑器内的完整功能。以下是第一轮报告里标注"未实测"的功能，本轮补充实测结果。

### 7.1 新建计划向导：目的地输入框直接支持自然语言，不是"地点搜索"和"AI想法"两个分开的入口
点击"新建计划"后弹出的"目的地"输入框，直接把我输入的完整句子"带两个小孩去杭州玩3天，喜欢亲子和杭州自然风光"原样存为一个可选项（不会强行拆解成一个具体地名），说明这一个输入框同时承担"地点自动补全搜索"和"自由描述想法交给AI理解"两种用途，而不是像首页视觉上呈现的"计划/解析"两个Tab那样割裂。
**为什么值得学**：这是一种"一个输入框、模糊意图也能兜底"的设计，用户不需要先判断"我该填地名还是描述想法"，降低了新用户在起点就要做选择的心智负担。

### 7.2 日期选择支持"确定日期"和"大概几天"两种模式，且自动识别用户所在时区
点击"行程时间"后弹出的日期选择器明确标注"时区：Asia/Kuala_Lumpur"——这是系统根据我（测试者所在的浏览器环境）自动识别出的时区，而不是固定写死的中国时区。同时提供两个平级Tab："确定日期"（标准日历，可选开始/结束日期）和"大概几天"（不绑定具体日期，只说大概天数）。
**为什么值得学**：
1. 自动时区识别对"旅记"的马来西亚用户群体直接相关——如果"旅记"以后要处理"目的地当地时间"和"用户所在时区"两套时间（比如提醒"该出发去机场了"），这种"用 `Intl.DateTimeFormat().resolvedOptions().timeZone` 自动取用户时区、而不是硬编码"的做法值得直接照搬，成本很低。
2. "大概几天"模式印证了第3.4节的判断——很多旅行灵感产生时用户根本还没定真正的出发日期,给"确定日期"之外一个更轻的替代选项,而不是逼用户先编一个假日期,是个值得借鉴的细节。

### 7.3 编辑器顶部工具栏：分享/协作/导出功能比第一轮推断的更具体，但也发现一个真实的隐私隐患
点击"分享"按钮后打开的"分享行程"弹窗包含（均为真实UI，非营销文案推断）：
- **行程链接** + "复制行程链接"按钮（真实的只读分享链接机制，非官方文案空谈）
- **邀请共同编辑** 按钮（真实入口，证实"多人协作"至少有UI层面的邀请机制，虽然本轮未测试双人同时编辑的实时同步效果）
- **导出文件格式** 按钮（点击后行程为空时提示"暂无可导出的行程"——说明导出功能确实存在，但要求行程里至少有内容才能导出；本轮因时间限制未能填充完整行程验证导出的word/图片实际文件效果）
- **分享图片（由AI生成）**：提供"路线手帐版"和"攻略卡片版"两种视觉风格，点击"生成图片并保存"可把整个行程一次性渲染成一张适合发小红书/朋友圈的图片，**每天限额10次**（"今日共剩余次数：10次"）
- **带口令码分享**：勾选后可生成一个类似小红书"口令"的分享码，别人输入口令码即可解析出行程

**⚠️ 发现的隐私隐患（"旅记"应避免）**：行程默认创建时是"仅自己可见"，但**点开"分享"弹窗这一个动作本身，就把可见性静默切换成了"获得链接者可见"**——顶部的可见性状态按钮从"仅自己可见"变成了"获得链接者可见"，且我并未点击任何"切换为公开"的按钮，只是打开了分享弹窗。这是一个容易被用户忽略的隐私默认值改变（用户可能以为只是"准备好链接以防要分享"，实际上从这一刻起任何拿到链接的人都能看到内容）。"旅记"如果做类似的分享功能，必须确保"打开分享面板"和"实际改变可见性"是两个需要用户明确操作的独立步骤，不能因为UI意图是"你可能想分享"就提前放宽权限。

**"分享图片AI生成"这个功能本身值得借鉴**：把行程渲染成一张信息图/手帐风格的图片，天然适配小红书/朋友圈的分享习惯,对"旅记"当前正在做的小红书招募测试用户策略（见[[feedback-ask-questions-one-at-a-time]]关联的项目记忆）而言，"生成一张好看的行程/账本总结图供分享"可能是比"文字导出"更有传播力的功能形态,建议列入中期评估。

### 7.4 地点详情卡：AI生成的介绍文案里"夹带"了门票价格信息，但仍然不是结构化的花费字段
点开已添加地点"故宫博物院"的详情卡，展示了：评分4.9、分类"景点"、AI生成的介绍段落（其中提到"旺季门票60元，淡季40元，需提前7天在官方小程序预约，周一闭馆"）、AI摘要的"真实评价"要点（如"建筑精美""文化厚重""珍宝丰富"，各配一行说明）、地址、官方评级"5A景区"、电话、"反馈问题"和"收藏"按钮。
**重要澄清（修正第一轮结论的细节）**：门票价格信息**不是完全没有**——AI会在介绍文字里提到大致票价，但这只是**只读的介绍性文字**，不是可编辑、可加总、可关联到"我这次实际花了多少钱"的结构化数据字段。第一轮报告"完全没有预算/花费功能"这一结论依然成立（因为用户无法把这条AI文案里的"60元"变成一笔实际记账），但措辞上应更精确为"没有结构化的花费记录能力，即便AI文案里偶尔带出参考价格"。
**值得借鉴的部分**：这种"点开一个地点，自动展示评分+AI摘要介绍+真实评价要点+官方地址电话"的一体化详情卡，减少了用户为了"这个地方值得去吗、大概要多少钱、怎么联系"而跳出APP搜索的次数。"旅记"如果整合类似的地点信息卡（哪怕只接入现有地图服务的POI详情，不用做自己的AI摘要），可以考虑在"备注"旁边加一个"AI提炼这个地点的必看信息"的辅助入口。

### 7.5 证实存在一个独立于"行程天数"的收藏夹实体
地点详情卡里有一个"收藏到收藏夹"按钮，与"添加到DAY 1"是分开的两个动作——证实了第3.4节基于Explore页"地点合集"推测的判断：pitravel确实有一个不绑定具体天数的"收藏夹"数据实体，用户可以先收藏一个地点、之后再决定要不要拖进某一天的行程。**这进一步支持"旅记"评估增加类似"心愿单"实体的建议**（见第6节中优先级建议5）。

### 7.6 新发现：单日"一键优化路线"、版本历史（真实证据支持"协作"能力）、内嵌客服入口
- **"一键优化路线"**：每个DAY标题旁有一个按钮，可以对当天已加入的地点一键重新排序以优化路线（本轮因该日只有1个地点未能测试多地点场景下的实际效果，但按钮UI和悬浮提示文案已确认存在）。**值得借鉴**：如果"旅记"的地图视图未来要支持多点路线，"一键重排"比"让用户手动拖拽调整顺序"更省力，尤其是对不熟悉当地地理的用户。
- **版本历史**：编辑器"更多操作"菜单里有"历史版本"，明确写"最多保留10个版本，5分钟后有修改将会被保存"，且每条版本记录都标注了编辑者身份（本轮实测显示为我登录账号的昵称"BX"+"创建行程"）。**这是比官方博客文案更可信的证据**，证明其后端确实按编辑者记录变更（协作场景下的基础设施已具备），而不只是单纯的营销说法。**值得借鉴**：无论"旅记"要不要做实时协作，"自动保存+可回滚的历史版本+记录是谁改的"这个模式本身就是任何多人共同编辑数据的应用都该有的安全网,建议后续评估"旅记"的家庭多成员协作要不要补上类似的版本历史/变更归属能力。
- **内嵌客服入口**：编辑器顶部"更多操作"菜单里直接放了"微信客服"和"表单反馈"两个入口,让用户在正在编辑行程、遇到疑惑的当下就能联系客服或提反馈,不需要跳出去找"关于我们"页面。**值得借鉴**："旅记"已有的反馈功能（`FeedbackSheet`）目前入口在"更多"里的一个入口，这与pitravel的做法基本一致，属于双方都做对的地方，无需改动，仅作为交叉验证记录。

### 7.7 本轮更新后的结论修正
- 第4.7节"完全没有花费记录能力"这一结论**依然成立**，但补充：AI生成的地点介绍文字里会顺带提及参考票价，只是纯文本、不可结构化利用，不影响"旅记"预算/汇率/拆账功能作为差异化优势的判断。
- 第4.6节"没有真实时间调度能力"**需要重要修正，见第8节的完整实测**：选定真实开始/结束日期后，DAY卡片确实会显示真实日期+星期（如"08.20 周四"），并非只有"DAY N"。第一轮"全文正则扫描无日期"的结论只适用于**编辑部公开模板**（这些模板本身大概率是用"大概几天"模式或手动规划、未绑定具体年份日期制作的，所以对外展示不含日期），不能代表产品能力上限。已在第8节用一个完整的"南京6天"真实案例更正这一点，请以第8节为准。

## 8. 完整实测案例：南京6天（第三轮，含真实AI智能规划全流程）

> 应用户要求，选择一个真实、完整、有明确时间范围的案例走完整流程："目的地=南京，日期=2026.08.20—08.25（6天5晚），偏好标签=经典必玩，走'智能规划'（AI一键生成）路径"，而不是像前两轮那样零散地点几个功能。

### 8.1 操作步骤
1. 首页点击"新建计划"，弹出向导。
2. "目的地"输入框直接打字"南京"，从自动补全下拉里选中"中国江苏省南京市"。
3. "行程时间"点开日期选择器，界面顶部显示"时区：Asia/Kuala_Lumpur"（自动识别我们所在时区），选择"确定日期"模式，点选 8月20日 → 8月25日，界面实时显示"8.20 - 8.25 · 6天"。
4. "旅行偏好"勾选"📍 经典必玩"标签。
5. 点击"智能规划"（而非"手动规划"），出现全屏loading："智能规划中 / 正在为你勾勒最棒的行程… / 取消规划"。
6. 约几秒后，AI生成完毕，自动跳转进入编辑器，直接呈现一份完整的6天行程。

### 8.2 AI生成结果的真实内容（完整摘录，未删减未加工）
生成的行程标题：**"南京市经典必玩6天行程"**（自动拼接了"目的地+选中的偏好标签+天数"），副标题："08.20至08.25 6天5晚"。

**每一天都有AI生成的主题名，不是"DAY 1/DAY 2"这种编号**：
| 日期 | 星期 | AI生成的当日主题 | 当日移动总里程 |
|---|---|---|---|
| 08.20 | 周四 | 牛首山与秦淮夜 | 18km |
| 08.21 | 周五 | 长江路与新街口 | 4km |
| 08.22 | 周六 | 钟山名胜全览 | 6km |
| 08.23 | 周日 | 南博与玄武湖畔 | 13km |
| 08.24 | 周一 | 颐和路City Walk | 17km |
| 08.25 | 周二 | 红山动物园收尾 | 10km |

**每个地点条目自带一段AI生成的实用介绍文案**（不用点开详情卡，列表里直接可见），例如：
- 南京牛首山文化旅游区："耗资40亿的佛顶宫震撼绝伦，地宫金碧辉煌，建议预留3小时深度游览，记得穿舒适鞋。"
- 明孝陵景区："世界文化遗产，石象路神道被誉为南京最美600米，清晨人少光影佳，6:30前可免费入园。"
- 古鸡鸣寺："门票10元含三炷香，登高可俯瞰紫峰大厦，百味斋素面人均20元值得一试。"

每条之间依然保留第3.1节说的"距离+耗时"提示（如"15.4千米 36分钟""958米 12分钟"）。

### 8.3 重要修正：真实日期+星期确实会显示，此前"无日期"的结论需要限定范围
这是本轮最重要的发现：**只要用户在创建时选择了真实的开始/结束日期，DAY卡片就会显示"08.20 周四"这种真实日期+星期，而不是抽象的"DAY 1"**。第一轮报告基于对"编辑部公开模板"全文的正则扫描得出"无日期绑定"的结论，现在看来那只是因为**那些公开模板本身很可能是用"大概几天"模式或手动规划、不绑定具体年份创建的**（毕竟"四月是属于杭州龙坞的"这种模板要能反复用于不同年份的读者，绑定具体日期反而不合理）。这不代表产品没有日期绑定能力——它有，而且做得还不错（连星期几都算出来了）。
**对"旅记"的影响**：不需要改变结论"旅记已有时间轴+日历双视图是差异化优势"，但对比时的措辞要更准确：优势不在于"pitravel完全没有日期"，而在于"旅记从一开始的核心浏览视图就是日历/时间轴，而不是需要用户在创建时选择走某条特定路径才能激活日期显示"。

### 8.4 新发现的产品缺陷：AI会把"暂停开放/暂停营业"的地点也排进行程
生成结果里包含了**4个明确标注不可用的地点**，AI依然把它们排进了正式行程：
- "美龄宫**(暂停开放)**"（08.22第2项）
- "中山陵景区**(暂停开放)**"（08.22第3项）
- "灵谷景区**(暂停开放)**"（08.22第5项）
- "红公馆(老门东店)**(暂停营业)**"（出现在"待计划"推荐池里）

也就是说，AI/地图数据库明明**已经知道**这些地点当前不可用（状态标签就直接拼在名字里），却没有在生成行程时把它们过滤掉或换成替代地点，导致用户如果不细看，会规划一整个上午去一个已经关闭的景点。
**"旅记"应避免**：如果"旅记"未来做AI行程生成或"附近推荐"功能，接入的地点数据只要带"暂停营业/暂停开放/已关闭"这类状态字段，就必须在生成/推荐逻辑里**主动过滤掉**，而不是仅仅在文案上加个括号提示——这是一个"数据其实是对的，但没有用在该用的地方"的典型工程疏漏，很容易在自己的实现里重复犯。

### 8.5 待计划推荐池里出现了已经排进正式行程的地点（轻微的重复/去重疏漏）
"老门东"在08.20正式行程第4项已经排入，但"待计划"推荐池里依然把"老门东"列为待选推荐——正常预期应该是"已经用掉的地点从候选池里移除"。这是一个较轻微的产品细节疏漏。
**"旅记"应避免**：如果未来做类似"待计划候选池"功能，候选池的过滤逻辑要包含"排除已经加入本行程任何一天的地点"，否则会让用户以为自己没有把某个地点加进去，造成困惑或重复添加。

## 附：本次调研中遇到的问题与局限

- 第一轮调研中，pitravel 的核心"新建计划""AI生成""复制为我的行程"等写操作均被登录墙拦截，严格遵守"不注册、不输入手机号验证码"的限制，因此对这些功能只能基于可见UI文案(输入框placeholder、按钮文案)和产品博客描述做**未实测**的合理推断，已在第2节表格中逐条标注。
- 第二轮调研（第7节）由用户本人在 Browser 面板里用自己的账号完成登录（手机号/验证码/密码全程由用户本人操作，我未接触），登录后我用该已登录会话继续测试，解锁了第一轮标注"未实测"的大部分功能。仍未能验证的部分：
  - **"多人实时协作编辑"的真实协同体验**（多人同时编辑的延迟、冲突解决）——本轮只确认了"邀请共同编辑"入口和支持按编辑者归属的版本历史这两项基础设施性证据，未做双账号同时编辑测试。
  - **选定真实开始/结束日期后，DAY卡片是否会显示具体日期**——本轮跳过了日期选择步骤直接进入手动规划，这一点仍需团队自行注册验证（见7.7节）。
  - **导出Word/图片的实际文件效果**——测试行程内容太少，触发了"暂无可导出的行程"提示，未能验证真实导出文件的排版质量。

  - **便签/清单/图库三个工具面板填入真实内容后的效果**——两轮调研都只确认了入口存在，未能实际打开验证。
