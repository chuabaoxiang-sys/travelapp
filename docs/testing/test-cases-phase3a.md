## 测试总结

**结果：129个用例全部通过（其中5个在测试过程中先发现真实问题、修复后复测通过：TC-54/TC-98为逻辑bug，TC-74/TC-80为遗漏功能/过期占位文案，TC-119为测试方法本身的错误）。**

- **阶段6顺带做了一次代码健康度清理**：`npm run lint` 之前有3条"一个文件混合导出组件和普通函数/常量"的警告（`categoryVisuals.tsx`、`MemberGate.tsx`），会影响开发时Fast Refresh的可靠性。既然这次是"测试与文档"收尾阶段，顺手把这3处拆开了：`categoryVisuals.tsx` 拆成纯逻辑的 `lib/categoryColors.ts` 和纯组件的 `components/CategoryBadge.tsx`；`MemberGate.tsx` 里的 `useCurrentMemberId` hook 拆到独立的 `useCurrentMemberId.ts`。拆完之后重新跑了一遍构建+测试+lint+浏览器实测，确认没有引入回归。
- **`fake-indexeddb` 让`computeBalances`这个全项目最核心的金额计算函数第一次有了真正的自动化测试**（此前只靠每个阶段的手动浏览器验证，测试通过后测试环境状态就丢弃了，不会随代码变更持续保护）。以后改动分摊/结算逻辑，跑一次 `npm run test` 就能立刻发现回归，不用每次都重新在浏览器里搭一遍测试数据手动核对。

- **阶段5的导出功能复用了`domain/splits.ts`里已有的`computeBalances`**做"按人汇总"，没有重新写一遍分摊/结算的计算逻辑——这样导出数据里的净额天然跟"分账"tab页面显示的完全一致（包括已经记录的结算抵扣），不会出现"导出的Excel和APP里看到的数字对不上"的问题。

- **阶段4实现过程中的一个插曲**：`registerOutboxHooks` 用到的 `SYNCED_TABLES` 常量最初被声明在 `export const db = new TripJournalDB()` 之后，但 `db` 实例化时构造函数会立刻调用 `registerOutboxHooks(this)`，而模块顶层代码是从上到下同步执行的——`SYNCED_TABLES` 这行代码在 `db` 实例化那行代码之后，意味着它在被引用的那一刻还处于"暂时性死区"，导致 `ReferenceError: Cannot access 'SYNCED_TABLES' before initialization`，整个APP直接白屏。这是我在自己验证生产构建时发现的（不是用户报告的），修复方式是把 `SYNCED_TABLES` 的声明挪到 class 定义之前。顺带在这轮验证里也修了两个 `tsc -b`（项目引用构建模式）才会暴露、之前单独跑 `tsc --noEmit` 没检测出来的类型错误——说明这个项目应该定期用 `npm run build` 做一次完整验证，不能只依赖零散的 `tsc --noEmit`。

- 首次执行时 TC-22（当日花费汇总/费用挂到具体行程项）因当时 `AddExpenseSheet` 还没有"挂到某天/某行程项"的关联UI而跳过——这是阶段3b的范围，阶段3a本不做。阶段3b把日历视图、地图视图（Leaflet+Nominatim真实选点）、以及记账时关联到具体行程项这三块补上后，回头把TC-22重新测过，已通过：给"参观天守阁"这个行程项挂了一笔RM478的门票费用，时间线视图正确显示该行程项旁边的RM478、以及"当日花费 RM478"的合计。
- **TC-54 测出真实bug**：编辑一笔已经关联了行程项的账目时，"关联到行程"区域虽然会自动展开，但里面的日期/行程项chip没有正确显示为选中状态。根因是 `AddExpenseSheet` 用 `useState(从itineraryDays.find()算出来的初始值)` 去回填，但 `itineraryDays` 是 Dexie 的异步查询（`useLiveQuery`），组件第一次渲染时这个查询还没跑完、返回的是空数组，所以算出来的初始值永远是空的——这是 React 里"用异步数据计算 useState 初始值"的经典坑。修复方式是改用 `useEffect` 监听 `itineraryDays`，等它真正查到数据后再回填一次（用一个 ref 标记只回填一次，避免后续重复覆盖用户自己的选择）。修复后用两台"虚拟设备"顺序验证过：day chip 和 item chip 都能正确显示为选中态。
- **TC-74 测出遗漏功能**：预算Tab最初实现时，总预算只有"编辑"入口，没有"删除"入口（分类预算有）。按用户此前明确定下的标准要求——"删除"和"编辑"功能必须纳入所有未来功能——这属于漏做，测试中发现后已补齐：加了删除按钮+复用同一个`ConfirmDialog`组件二次确认，删除后总预算区域正确回到"还没设置"的初始态。
- **TC-80 测出过期占位文案**：记账Tab的"已花费"卡片下方原本写死显示"预算与超支提醒将在下一阶段加入"——这是阶段3a/3b/3c遗留的占位说明，阶段3d把预算功能实际做完后忘记替换。测试中发现后已修复为读取真实的总预算数据，动态显示"距总预算还剩 RMxx"或"已超出总预算 RMxx"，未设总预算时不显示任何文字（不再有过期承诺）。
- 分摊/结算的核心算法（`resolveSplitShares`均分逻辑、`computeBalances`按人汇总、`simplifyDebts`贪心债务简化）用多组真实金额场景手工核算后逐一比对界面显示，包括3人均分、2人均分（含改分摊人数后的实时重算）、以及"不分摊"边界情况（全部取消勾选后账目全额算入付款人自己名下），全部与预期完全一致。
- **TC-98 测出真实bug**：一开始"个人开销/大家分摊"开关是从 `splitMemberIds.length` 直接推导显示状态（`length===0` 才算个人开销）。但编辑一笔已保存的个人开销账目时，它的分摊明细固定是"付款人自己一条记录"（`length===1`，不是0），推导逻辑就会误判成"大家分摊"模式，开关显示错误、选人区也跟着错误展开。另外这个推导方式还有第二个隐患：用户在"大家分摊"模式里手动取消勾选到只剩1人时，界面会突然塌成"个人开销"的样子，打断正在进行的选择操作。改为用独立的 `mode` 状态（初始值直接读取 `expense.splitType` 这个同步字段，不用等异步查询），开关只负责"整笔怎么算"这个粗粒度切换，选人区里手动调整人数不再意外触发模式突变。
- 结算记录会正确进入`computeBalances`的净额计算：`net = (paid - owed) + settledOut - settledIn`，用部分结清、全额结清、撤销结清三种场景手工核算后跟界面比对，全部一致。
