## 1. 问题陈述（Problem Statement）

### 1.1 这是为谁做的

这不是一款面向大众市场的旅游 App，而是**为一个具体的家庭**（居住在马来西亚、日常使用中文沟通）定制的私有工具。使用者是这一家人自己——可能是 2 到 5 位家庭成员，在多趟旅行中共同记录行程与花销。目标用户不是"某个细分市场的旅行者画像"，而是这个家庭本身：他们的语言习惯（中文）、本位币（马币 MYR）、记账习惯（多人分摊、跨境消费）就是产品设计的直接输入，不需要做市场细分或多语言/多币种默认值的通用化设计。

### 1.2 要解决的问题

这个家庭每次出行都面临两类真实、反复出现的痛点：

**行程记录侵蚀记忆**：一趟旅行结束几个月后，家人常常记不清"那天到底去了哪几个地方、几点到的、路线是怎么走的"。行程安排目前散落在聊天记录、订票邮件、随手笔记里，缺乏一个统一、按天组织、事后仍可回顾的记录，也没有可视化的路线呈现。

**多币种记账的汇率痛点是核心矛盾**：出行前的开销（保险、机票、签证）和途中开销（餐饮、交通、购物）分散发生，且往往涉及三个不同的汇率——订票时银行卡的汇率、换现金时的汇率、当地刷卡消费时的汇率。如果每次记一笔外币开销都要重新查汇率、手动输入，记账会变得繁琐到让人放弃；但如果为了省事就随便估一个汇率，账目又会失真，事后没法准确知道"这趟一共花了多少马币""每个人该分摊/该收多少钱"。

**不解决这两个问题的代价**：行程记录不做，家庭旅行的记忆会随时间流失，无法整理成有意义的回顾内容；账目不做或做得潦草，家人之间的费用分摊会靠模糊记忆和口头协商，容易产生"到底谁垫付了多少、该找谁结算"的小摩擦，长期积累的多趟行程数据也没有办法沉淀下来复用（比如"上次去日本时现金汇率是多少"）。

### 1.3 证据

这是一个从真实家庭需求出发、经过多轮澄清确认的自建项目，证据来源是与产品使用者（家庭发起人）的直接需求访谈与决策确认（详见实施计划文档中的决策记录），而非市场调研或行为数据——这符合小型自用工具的验证方式：**验证的方法是"这一家人以后旅行时是否真的打开它用"，而不是问卷或点击率**。

## 2. 目标与成功指标

本产品服务对象是单一家庭，因此**成功标准是真实使用，不是增长指标**。不设 DAU/MAU、留存率、转化率这类面向多用户产品的指标。

| 目标 | 衡量方式 | 当前基线 | 目标 | 衡量窗口 |
|------|---------|---------|------|---------|
| 家人愿意在真实旅行中使用行程记录功能 | 下一趟实际出行中，是否用 App 记录了至少 80% 的行程天数 | 0（尚未存在） | 是 | 上线后第一趟实际出行 |
| 家人愿意在真实旅行中用它记账，而不是退回 Excel/口头记账 | 一趟行程结束时，App 内记录的总开销是否覆盖家人主观估计的"大部分开销" | 0 | 覆盖主观估计的 90% 以上开销 | 上线后第一趟实际出行 |
| 汇率簿确实减少了重复输入汇率的烦恼 | 途中记外币账时，"一键复用已有汇率标签"被使用的比例 | 0 | 70% 以上的外币记账使用已有标签而非每次新建 | 上线后第一趟实际出行 |
| 离线记账不丢数据 | 一趟行程中若有离线记录，恢复网络后是否 100% 成功同步、无数据丢失 | 0 | 100% | 每趟行程 |
| 行程结束后账目结算不再靠口头协商 | 是否使用 App 的按人统计/结算页完成实际的家庭内部结算 | 0 | 是 | 每趟涉及多人分摊的行程 |
| 数据导出真的被使用 | 行程结束后是否实际导出过 Excel 或 JSON/CSV（无论是为了留档还是喂给外部 AI 工具） | 0 | 至少一次/趟 | 行程结束后 30 天内 |

以上指标的评估方式是**每趟行程结束后，产品负责人（即家庭内部维护这个 App 的人）主观复盘 + 直接询问家人**，不需要建立数据分析仪表盘。

## 3. 两大同等优先级功能支柱

本产品有两个**并列、同等重要**的功能模块，不存在主次关系，两者共享同一趟"行程（trip）"作为组织单位，并通过费用与行程项的关联字段互相打通。

### 支柱一：行程记录（Itinerary Recording）

按天记录一趟旅行的具体安排——去哪里、几点到、做什么、备注什么，并支持切换"时间线视图"与"日历视图"两种呈现方式查看同一份数据，同时把有经纬度信息的地点在地图上可视化成路线/轨迹。行程记录是账目记录的"骨架"——每一笔花费都可以（但不强制）挂到具体某一天甚至某个具体行程项上，这样在查看某一天的行程时，能直接看到当天花了多少钱。

### 支柱二：行程账目管理（Trip Finance Tracking）

记录一趟旅行出发前和途中的所有开销，核心难点是多币种、多汇率的准确处理——**汇率簿（Rate Book）**机制让每趟行程、每种外币可以保存多个带标签的常用汇率（如"现金汇率""信用卡汇率""订票汇率"），记账时一键选用，避免每次重新输入,同时用免费汇率 API 提供参考值但始终可手动覆盖。在此基础上支持预算设置与超支提醒、费用在家庭成员间的分摊与按人结算。

两大支柱**都要在 v1 中并行、完整地交付**，不能出现"账目模块做得很细、行程模块只是附属"或反之的情况——这是本次需求中被明确强调、不可动摇的优先级设定。

## 4. 支撑性功能（Supporting Features）

这些功能服务于两大支柱，本身不构成独立的产品支柱，但同样属于 v1 范围：

- **离线记录 + 自动同步（PWA）**：整个 App 可安装到手机主屏幕，完全断网状态下也能打开使用（行程记录和账目记录都要支持离线写入），网络恢复后自动把离线期间的改动同步到云端数据库，界面上有明确的同步状态提示。
- **Excel 导出**：一次导出生成一个多 Sheet 的工作簿，同时覆盖行程和账目两块数据，包含"明细"Sheet（逐条记录）和"汇总"Sheet（按天/按分类/按人汇总）。
- **结构化数据导出（JSON/CSV）**：把行程和账目数据导出为字段清晰、结构干净的 JSON 或 CSV 文件，定位是方便用户自行喂给外部 AI 工具（如 ChatGPT、Claude、短视频脚本生成工具）——**App 本身不内置任何 AI 生成能力**，只负责导出干净的数据。
- **行程只读分享链接**：为一趟行程生成一个公开的只读链接，分享给行程之外的朋友查看行程安排（时间线/日历/地图），链接**不包含任何账目数据**，且不可编辑。

## 5. 非目标 / v1 明确不做的范围（Non-Goals）

以下内容是本次需求讨论中被**明确排除**的范围，写明在此是为了防止开发过程中的范围蔓延（scope creep）。任何人（包括产品负责人自己）在开发过程中想加入以下内容，都应先视为一次新的变更请求走评估流程，而不是默认并入当前迭代：

| 排除项 | 排除原因 | 未来是否可能重新评估 |
|--------|---------|---------------------|
| 登录/账号认证系统 | 单一家庭内部信任模型足够，共享链接进入后手动选择"记账人"姓名即可；`auth_user_id` 字段已在数据模型中预留，未来加真登录不需要推翻表结构 | 若家庭规模扩大或需要对外开放，可重新评估 |
| 收据照片上传 | 非本次讨论中确认的核心需求，架构上不堵死（`itinerary_item`/`expense` 表结构留有备注/附件扩展余地），但 v1 不实现 | 若家人反馈"想留存收据"信号明确，可在 v2 加入 |
| 出行前待办清单（checklist） | 在两轮需求澄清中被用户明确表示"不需要" | 除非用户主动重新提出，否则不纳入 |
| 订票信息/证件留存 | 用户在多选题中未选择该项 | 同上 |
| 图文游记/回忆录呈现 | 用户在多选题中未选择该项，且导出功能已经为"用户自行生成游记内容"提供了数据基础 | 若导出+外部 AI 的组合被验证不够用，可重新评估内置呈现能力 |
| PPT 导出 | 明确列为"未来方向"，但 v1 数据组装层设计已做到与渲染格式解耦，未来加 PPT 渲染器是增量工作 | 已有明确的技术路径，视需要程度排期 |
| 内置 AI 内容生成（游记文案、短视频脚本等） | 本产品定位是"导出干净数据交给外部工具"，不重复造轮子内置 AI 能力 | 短期内不评估；除非外部工具的数据消费方式发生重大变化 |
| 真正的访问控制/权限体系 | "无登录"和"只读分享链接"都是基于信任的模型，不是安全边界；这是设计上的取舍，不是遗漏 | 如果未来分享场景扩大到不完全信任的对象，需要重新设计 |

## 6. 用户画像

**主要角色：家庭记账人（可以是任意一位参与旅行的家庭成员）**
- 中文为主要使用语言，居住在马来西亚，本位币是马币（MYR）
- 会在出发前记录预订类开销（保险、机票、签证），在途中随手记录每一笔消费
- 会遇到多币种消费（当地货币），希望记账时不必每次重新计算汇率
- 期待旅行结束后能清楚看到"这趟一共花了多少钱、谁该找谁结算多少钱"
- 可能在没有网络的地方（如飞机上、境外无信号区域）记录行程或账目，期待恢复网络后自动同步，不需要手动操作

**次要角色：行程之外的朋友（分享链接的访问者）**
- 通过一个只读链接查看这家人某趟行程的时间线/日历/地图安排
- 不需要、也看不到任何账目信息，也不能编辑任何内容

## 7. 核心用户故事与验收标准

以下故事覆盖 v1 的核心使用流程，均以"给定—当—则"（Given/When/Then）的方式给出验收标准，确保开发和测试有明确、可核对的完成定义。

### 故事 1：创建一趟新行程

作为家庭记账人，我想创建一趟新的行程，以便后续的行程安排和账目记录都能挂在这趟行程下面。

**验收标准**：
- [ ] Given 我打开 App 首页，When 点击"新建行程"，Then 我可以填写行程名称、起止日期、本位币（默认预填 MYR，可修改）。
- [ ] Given 我保存了新行程，When 保存成功，Then 系统自动生成该行程记录，并跳转到该行程的行程记录页（默认视图为时间线）。
- [ ] Given 我此前已经创建过其他行程，When 我在新建行程时选择了一个曾经用过的外币，Then 系统提示"是否复制该币种在历史行程中使用过的汇率标签"，我可以选择"复制"或"跳过"（对应实施计划中的加分项设计）。
- [ ] Given 我尚未添加任何家庭成员，When 我创建行程，Then 系统允许我在行程详情页随时添加/选择参与本趟行程的家庭成员（选人机制，不需要登录）。
- [ ] Given 我离线（无网络），When 我创建新行程，Then 行程仍能成功创建并在本地可见，且被加入待同步队列（见故事 8）。

### 故事 2：添加行程日程（按天 + 具体行程项）

作为家庭记账人，我想按天记录当天的安排（去了哪些地方、做了什么），以便日后回顾整趟行程的路线和细节。

**验收标准**：
- [ ] Given 我在某趟行程的行程记录页，When 点击"添加一天"，Then 我可以选择该行程日期范围内的某一天，填写当天标题/摘要与备注。
- [ ] Given 我已经创建了某一天，When 点击"添加行程项"，Then 我可以填写标题、可选的时间点、地点名称，并通过地点搜索（基于 Nominatim）选点后自动写入经纬度；地点搜索框有输入防抖，不会在快速打字时对搜索服务发起过量请求。
- [ ] Given 某个行程项没有填写具体时间，When 在时间线视图查看当天，Then 该行程项仍会显示，但排在有具体时间的项目之后（或按用户手动排序的顺序），不因缺少时间而报错或无法保存。
- [ ] Given 我已经为某一天添加了多个行程项，When 我切换到"日历视图"，Then 我看到的是同一份数据以月历/日历形式呈现，而不是需要重新输入。
- [ ] Given 某个行程项填写了经纬度，When 我打开地图视图，Then 该地点会显示为地图上的一个标记，且同一天/同一趟行程的多个地点会按时间顺序连成路线；地图图层显示 OpenStreetMap 版权署名。
- [ ] Given 我离线记录了某一天的行程，When 网络恢复，Then 该记录自动同步（复用与账目记录相同的离线同步机制）。

### 故事 3：使用汇率簿记录一笔外币消费（核心故事，最高优先级）

作为家庭记账人，我想在记一笔外币消费时，能够一键复用之前用过的汇率标签，而不必每次重新查汇率、手动输入，同时保证历史记录的汇率不会被之后的修改影响。

**验收标准**：

*基础流程*
- [ ] Given 我在某趟行程中添加一笔新费用，When 选择的币种就是本位币（MYR），Then 系统跳过汇率相关步骤，直接输入金额即可保存。
- [ ] Given 我选择的币种是外币，When 进入汇率选择环节，Then 系统展示该趟行程、该币种下"最近使用"和"最常使用"的汇率标签列表（如 `[现金汇率 4.35]` `[信用卡汇率 4.42]`），并提供一个 `[+ 新汇率]` 选项；标签的排序依据是使用次数和最近使用时间。
- [ ] Given 汇率标签列表中已有我需要的标签，When 我点击该标签，Then 系统立即用该标签对应的汇率数值完成折算并预填到"折算后本位币金额"字段，无需再输入任何汇率数字。

*新建汇率标签*
- [ ] Given 我点击 `[+ 新汇率]`，When 输入标签名称，Then 输入框基于该行程/币种下历史用过的标签名称做自动补全提示。
- [ ] Given 我在新建汇率环节且设备联网，When 汇率输入框加载，Then 系统调用 Frankfurter（或备用 API）自动预填一个参考汇率值，并在界面上清楚标注"参考汇率，可修改"，不会让用户误以为这是不可更改的官方值。
- [ ] Given 我在新建汇率环节但设备离线或 API 调用失败，When 汇率输入框加载，Then 该字段留空，允许我手动输入汇率数值，不报错、不阻塞保存流程。
- [ ] Given 我手动修改了 API 预填的参考汇率，When 保存这笔费用，Then 系统记录该汇率标签的来源为"API 修改"（而非"API 采纳"或"手动"），供未来审计/回顾使用。
- [ ] Given 我成功保存了一个新的汇率标签，When 我下次在同一趟行程、同一币种下记账，Then 该标签出现在可复用的标签列表中（验证"一次新建，之后可复用"）。

*金额计算与历史不可追溯变更*
- [ ] Given 我选定了汇率（无论来自已有标签还是新建），When 我保存这笔费用，Then 系统按"外币金额 × 所选汇率"计算出本位币金额，并把**当时的汇率数值和折算结果作为快照**永久保存在该笔费用记录上。
- [ ] Given 某笔费用已经保存（快照了某个历史汇率值），When 我之后在汇率簿管理页编辑了同一个标签对应的汇率数值，Then 这笔已保存的历史费用记录的汇率和折算金额**保持不变**，不会被追溯修改；只有之后新记的费用才会使用编辑后的新汇率值。
- [ ] Given 我想让某个标签之后使用不同汇率、但不想影响这个标签的历史含义，When 我在汇率簿管理页选择"另存为新标签"，Then 系统创建一个新标签（如"信用卡汇率(8月)"），原标签不受影响。

*汇率簿管理页*
- [ ] Given 我打开某趟行程的汇率簿管理页，When 页面加载，Then 我能看到该行程下所有币种、所有标签及其当前汇率值、使用次数、最近使用时间。
- [ ] Given 某个标签已经不再使用，When 我选择"归档"，Then 该标签不再出现在记账时的快速选择列表中，但历史费用记录（已快照汇率）不受影响，且归档标签仍可在管理页中查看或取消归档。

*边界情况*
- [ ] Given 我是第一次为某趟行程的某个新币种记账（没有任何历史标签），When 进入汇率选择环节，Then 系统直接展示 `[+ 新汇率]` 的新建流程，不因为没有历史数据而报错。
- [ ] Given 汇率数值填写为 0 或负数，When 尝试保存，Then 系统阻止保存并提示汇率必须为正数。

### 故事 4：将一笔费用关联到具体某一天/某个行程项

作为家庭记账人，我想把一笔费用挂到具体的某一天甚至某个具体的行程项上，以便查看行程时能直接看到当天/该项目花了多少钱。

**验收标准**：
- [ ] Given 我在记录一笔费用，When 填写费用表单，Then 我可以选择性地关联到该趟行程下的某一天（`itinerary_day`），此关联为可选，不填写也能正常保存费用（对应"出发前"阶段的开销通常不需要关联到具体某天）。
- [ ] Given 我已经选择了关联的某一天，When 该天下存在具体行程项，Then 我可以进一步选择性地关联到某个具体行程项（`itinerary_item`）；若选择了具体行程项，其所属天必须与我在上一步选择的天一致，系统需保证这种一致性，不允许出现"行程项属于 A 天，但费用关联的天却是 B 天"的数据不一致。
- [ ] Given 一笔费用已经关联到某一天，When 我在行程记录的时间线或日历视图中查看那一天，Then 该天的卡片上能看到当天关联费用的汇总金额（本位币）。
- [ ] Given 一笔费用已经关联到某个具体行程项（如"上午：环球影城"），When 我查看该行程项详情，Then 能看到关联到该项目的费用明细和小计。
- [ ] Given 我修改了某笔费用的天/行程项关联，When 保存修改，Then 原关联天/行程项和新关联天/行程项对应的汇总金额都相应更新，不会出现"账还挂在旧的天上"的情况。

### 故事 5：设置预算并在超支时得到提醒

作为家庭记账人，我想为整趟行程或某个费用分类设置预算，以便在快要超支或已经超支时得到提醒。

**验收标准**：
- [ ] Given 我在某趟行程的预算设置页，When 我新建一条预算，Then 我可以选择该预算是针对"整趟行程总额"还是"某个费用分类"，并填写预算金额（本位币）和一个超支提醒阈值（如"达到 80% 时提醒"）。
- [ ] Given 已设置的预算存在，When 该趟行程下累计费用（已折算为本位币）达到或超过提醒阈值，Then 界面上出现明显的提醒（如预算进度条变色、提示文案），但不阻止用户继续记账。
- [ ] Given 累计费用超过预算金额 100%，When 我查看该预算或该趟行程总览，Then 明确显示"已超支"及超支具体金额，而不是仅仅停在"接近预算"的提示级别。
- [ ] Given 预算是针对某个费用分类设置的，When 该分类下的费用发生变化（新增/修改/删除），Then 对应分类预算的进度实时重新计算，不需要手动刷新触发。
- [ ] Given 一趟行程没有设置任何预算，When 我查看行程总览，Then 不显示任何预算相关的进度条或提醒，只正常显示总花费，不因缺少预算设置而报错。

### 故事 6：在家庭成员之间分摊一笔费用并查看结算结果

作为家庭记账人，我想在记一笔费用时指定由哪些人分摊、如何分摊，并在行程结束后清楚看到谁该找谁结算多少钱。

**验收标准**：
- [ ] Given 我记录一笔费用，When 填写分摊信息，Then 我可以选择"不分摊（仅记录支出）"、"平均分摊给选定的几位成员"，或"按自定义金额/比例分摊给选定成员"。
- [ ] Given 我选择了"自定义金额分摊"，When 各成员分摊金额之和与该笔费用总金额不一致，Then 系统阻止保存并提示差额，直到分摊金额之和与总金额一致（或提供"自动补齐差额到某位成员"的便捷操作）。
- [ ] Given 一笔费用记录了"支付人"（谁实际付了钱）和"分摊明细"（谁该承担多少），When 我打开该趟行程的按人统计/结算页，Then 我能看到每位成员"实际支付总额"与"应承担总额"的差值，以及基于这些差值汇总出的"谁该转账给谁、多少钱"的建议结算方案（类似 Splitwise 的净额结算逻辑）。
- [ ] Given 某笔费用没有设置分摊（仅记录支出），When 计算按人统计，Then 该笔费用不计入任何人的"应承担"分摊，只计入支付人的"实际支付"，除非用户后续为其补充分摊设置。
- [ ] Given 一趟行程涉及多币种费用，When 计算按人统计和结算方案，Then 所有金额均按各笔费用保存时快照的本位币折算金额汇总，不重新按当前汇率折算，确保结算金额与账目记录一致、可复核。

### 故事 7：在完全离线的情况下记录行程/账目，并在恢复网络后自动同步

作为家庭记账人，我想在没有网络（如境外无信号、飞机上）的情况下依然能正常使用 App 记录行程和账目，并在网络恢复后不需要手动操作就能同步到云端。

**验收标准**：
- [ ] Given 设备处于完全离线状态（飞行模式），When 我打开已安装到主屏幕的 PWA，Then 应用外壳（界面、已加载过的数据）正常打开，不依赖当次网络请求，不停留在空白/加载失败页面。
- [ ] Given 设备离线，When 我新建行程、添加行程日程、记录费用（包括新建汇率标签，若离线则相应字段留空手动输入），Then 所有操作都能立即成功保存到本地存储，界面表现与联网时一致，不出现"需要联网才能保存"的报错。
- [ ] Given 我在离线期间进行了若干操作，When 我查看界面上的同步状态标识，Then 能看到清楚的"N 条记录待同步"提示，而不是让用户误以为已经同步。
- [ ] Given 设备恢复网络连接，When 应用检测到网络恢复，Then 自动（无需用户手动点击"同步"按钮）按操作发生顺序把待同步队列中的记录提交到云端数据库，同步状态标识相应更新为"已同步"。
- [ ] Given 同步过程中某一条记录提交失败（如网络短暂中断），When 系统重试，Then 该记录会自动重试直至成功，且不会因为一条失败而阻塞队列中其他记录的同步；同步状态标识清楚显示"同步失败，重试中"而不是静默失败。
- [ ] Given 两位家庭成员各自在离线状态下修改了同一条记录，When 双方恢复网络后先后完成同步，Then 系统按"更新时间戳，后写覆盖"的简化策略解决冲突（不做合并 UI），且这一行为已在使用说明文档中向家人明确说明,家人知晓可能出现的编辑丢失场景。
- [ ] Given 一条记录在本地成功保存并被加入同步队列，When 提交到云端，Then 系统使用客户端生成的 UUID 作为幂等标识做 upsert，即使因网络问题重复提交，云端也不会产生重复记录。

### 故事 8：将一趟行程的行程记录与账目导出为 Excel

作为家庭记账人，我想把某趟行程的行程安排和账目数据一次性导出为一份 Excel 文件，既留档，也方便查阅/分享给不使用这个 App 的家人。

**验收标准**：
- [ ] Given 我在某趟行程的详情页，When 点击"导出 Excel"，Then 浏览器直接生成并下载一个 `.xlsx` 文件，不需要等待服务器处理或额外的网络往返。
- [ ] Given 导出的 Excel 文件已生成，When 打开该文件，Then 至少包含两个 Sheet："明细"（逐条列出行程项与费用记录，字段包含日期、地点/分类、原始币种金额、折算后本位币金额、支付人、备注等）和"汇总"（按天、按分类、按人分别汇总的统计表）。
- [ ] Given 该趟行程既有行程记录又有账目记录，When 导出，Then 两类数据同时包含在同一份工作簿中，而不是拆分成两个文件。
- [ ] Given 该趟行程中某些费用没有关联到具体某天/行程项，When 查看导出的"明细"Sheet，Then 这些费用仍正常列出，关联字段留空即可，不影响导出成功。
- [ ] Given 我核对导出文件中的金额，When 与 App 内该趟行程的实际记录逐条比对，Then 数字完全一致（不允许因为导出逻辑独立于展示逻辑而产生差异）。

### 故事 9：生成一个只读的行程分享链接给行程外的朋友

作为家庭记账人，我想生成一个只读链接分享给不在这趟行程里的朋友，让他们看到行程安排，但完全看不到、也不能修改任何账目数据。

**验收标准**：
- [ ] Given 我在某趟行程的详情页，When 打开"分享"设置并启用分享，Then 系统生成一个随机、不易被猜到的分享 token，并给出一个可直接复制的公开链接（形如 `/share/:token`）。
- [ ] Given 分享链接已生成，When 任何人（无需登录、无需选择记账人身份）在浏览器打开该链接，Then 只能看到该趟行程的行程记录（时间线/日历/地图视图），完全无法看到任何账目相关的入口、数字或提示。
- [ ] Given 有人通过分享链接查看行程，When 检查该页面发出的网络请求，Then 不存在任何对账目相关数据表/接口的请求——账目数据的排除发生在查询层，而不仅是界面上"不显示"（这是安全验证的关键点，需在测试阶段专门核对）。
- [ ] Given 分享链接的访问者，When 尝试在分享页面进行任何编辑操作，Then 不存在任何可编辑的入口（新增/修改/删除按钮均不渲染），该页面纯只读。
- [ ] Given 我想撤回已分享的链接，When 我在行程详情页关闭"启用分享"开关，Then 该链接立即失效（后续访问该 token 应返回"链接已失效"而不是继续展示行程数据）。
- [ ] Given 我重新启用分享，When 系统生成分享设置，Then 需明确：是复用原 token 还是生成新 token，产品默认选择是**生成新 token**，以保证被转发出去的旧链接在重新启用后不会自动恢复访问（此为需要在设计评审中与开发确认的细节，若技术实现选择复用旧 token，需在用户使用说明中明确告知）。

## 8. 关键产品决策与取舍说明

以下决策已在需求讨论中确认，在此重申其取舍逻辑，避免开发或验收阶段被重新质疑：

- **无登录设计**：选择"进入后手动选择记账人姓名"而非账号登录，是因为这是单一家庭、彼此高度信任的私有工具，账号系统的复杂度对这个场景是过度设计。取舍是：任何拿到分享链接或本应用访问权限的人都可以任何家庭成员的身份记账/改动，这不是安全边界，是信任模型。`auth_user_id` 字段已在数据模型中预留，为未来收紧权限留出路径，但不会自动生效。
- **离线冲突策略选择"后写覆盖"而非合并 UI**：因为这是单家庭低并发场景，构建复杂的冲突合并界面的投入产出比很低。取舍是两人同时离线修改同一条记录时会丢失其中一次编辑，产品负责人需要让家人知情这一简化。
- **汇率簿的"快照不追溯"设计**：历史费用记录保存的是记账当时的汇率快照，之后编辑汇率标签或分类不会改变历史记录。这保证了账目的可审计性（"这笔钱当时是按什么汇率算的"永远可追溯查证），代价是如果用户发现历史汇率填错了，需要手动编辑该笔费用本身,而不是通过修改汇率簿一次性修正所有相关历史记录。
- **只读分享链接不是访问控制**：token 是随机字符串，不易被猜到，但不是加密权限系统。链接一旦被转发，任何拿到链接的人都能看到该趟行程的安排。账目数据的保护是通过"查询层完全不涉及账目表"实现的，是本产品在"无登录"前提下能够提供的最强隔离,但仍需要让用户理解这不等同于强访问控制。
- **v1 的非目标不是能力上限，是范围纪律**：本文档第 5 节列出的排除项，很多在架构上都预留了扩展空间（如附件字段、PPT 渲染器接口），排除的原因是"当前没有被验证的真实需求"，不是"技术做不到"。这样设计是为了避免 v1 交付被不断新增的"顺手加一个"功能拖慢。
