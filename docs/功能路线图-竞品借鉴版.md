# 旅记功能路线图 —— 基于 pitravel 竞品分析（免费优先，付费后置）

> 当前阶段：**免费档冲刺期**（暂无稳定收入来源，优先把免费能做的功能打磨完、上线、收集真实用户反馈；不投入任何按调用量计费的付费服务）。
> 这一行请随项目状态更新——一旦"旅记"开始有稳定收入（哪怕很少），把这里改成"可评估付费档"，并在第6节记录触发这个判断的具体信号。

## 0. 这份文档是什么、怎么用

这是 `docs/竞品分析-pitravel.md`（三轮竞品实测调研，共8节+附录）的**决策提炼版**。原文档记录的是"pitravel 有什么、哪里好、哪里不好"的调研证据；这份文档只回答一个问题：**这些值得借鉴的点，哪些现在就能免费做，哪些要花钱、所以先放着**。

给后续任何一次开发会话（不管是用户自己写、还是Claude Code接手）用的方法：
1. 先看第1节的分类标准，再看第2节（🟢现在就做）——这是当前唯一应该消耗开发时间的清单。
2. 第3、4节（🟡🔴）不要现在做，只是记下来、别忘、别重复调研，等触发条件（第6节）出现再回来看。
3. 每完成一项，把对应表格行的"状态"列改成 `✅ 完成于 YYYY-MM-DD`，如果做了但和原计划不一样，简单写一句为什么。
4. 每次有新的竞品调研（不止pitravel），在对应分类下追加新的表格行，标注来源文档，不要覆盖旧内容。
5. 想知道某一条的详细证据（比如pitravel具体是怎么做的、截图级别的实测过程），去 `docs/竞品分析-pitravel.md` 查对应章节号，本文档每条都标了来源章节。

**"旅记"当前已有、不需要再花钱验证的技术底子**（写在这里防止重复评估）：Vite+React+TS 前端，Dexie(IndexedDB) 本地优先存储，Supabase 做认证(邮箱magic-link)+云同步+按household隔离数据，已有 PWA 离线能力，已有时间轴/日历双视图，已有多币种汇率簿+预算+拆账结算，已有 Excel/JSON/CSV 导出 + Web Share API 分享，已有 `FeedbackSheet` 反馈入口。这些都是相对pitravel的现有差异化优势，不在下面的"要做的事"清单里，只是背景。

**一个待确认的开放问题（会影响第3节怎么排期）**：旅记现有的地图视图具体接的是哪家地图服务（Google Maps / Mapbox / Amap / Leaflet+OpenStreetMap 等）、有没有可用的 Directions/Places 相关能力？如果已经在用某个带免费额度的地图SDK，第3节里好几条可能"顺手就能做"，不算新引入付费依赖；如果目前只是纯展示型地图（无路线/地点搜索能力），那第3节才算真正的新增第三方依赖。**建议在开始排期第3节任何一条之前，先确认这一点。**

## 1. 分类标准

- 🟢 **免费档**：不依赖任何按调用量/按月计费的第三方服务，只需要开发工时（UI实现、本地数据模型、简单几何/贪心算法、内容创作等）。
- 🟡 **免费额度档**：依赖第三方 API，但在"旅记"当前的家庭级用户规模（个位数到几十个家庭）下，大概率长期落在对方的免费额度内；用户规模变大后需要重新评估。
- 🔴 **付费档**：功能的核心价值直接依赖一个明确按调用量计费的服务，主要是两类——**LLM API**（AI生成文案/行程/摘要）和 **地图POI/Places 类数据库API**（附近推荐、评分、地点详情）。在"旅记"还没有收入前不建议投入。

## 4. 🔴 付费档：先攒用户反馈、等有稳定收入再评估

| # | 功能 | 来源 | 为什么先不做 | 大概需要接哪类服务 |
|---|---|---|---|---|
| 1 | AI一句话/一键生成完整行程 | 8.2 / 6-11.5 | 核心是按token计费的LLM调用，南京6天案例证明生成质量上限确实高（每日主题名+每地点实用文案），但没有用户量之前无法判断这个功能能带来多少留存/转化，投入产出比不明 | 任意LLM API（不绑定具体供应商） |
| 2 | 每个地点的AI摘要简介 + AI摘要"真实评价" | 7.4 | 同上，且依赖地点评论数据源，属于"两个付费依赖叠加"的重型功能 | LLM API + 点评/POI数据源 |
| 3 | "附近推荐点位"发现式加点面板 | 3.2 / 6-8 | 需要真正的POI/Places数据库查询（按类别聚合周边地点），用量通常比单纯的地点搜索自动补全大得多，容易超出免费额度 | 地图服务商的Places/POI搜索API |
| 4 | AI个性化生成分享图片 | 7.3 / 6-10 | 第2节第11条的免费模板版已经能覆盖"生成好看的可分享图片"这个核心需求；AI版本的增量价值（更"懂"这次旅行的个性化文案/配色）值不值得付费，建议等免费版上线、看用户反馈再判断 | 图片生成或LLM服务 |
| 5 | 小红书/公众号链接自动解析成行程 | 3.3 / 6-12 | 除了抓取/NLP的服务费用，还有内容版权和平台反爬的合规风险——**这条即使有钱也要谨慎**，建议长期观察项，不只是攒钱的问题 | 内容抓取服务 + LLM地点抽取 |
| 6 | 通用格式（任意自然语言写的Word/PDF游记攻略）自动识别生成行程 | 第2节第16条的边界情况 | 第2节第16条的免费规则解析器只认得pitravel这种固定表格结构；如果换成自然语言写的游记，没有固定模式可抓，必须靠LLM理解语义才能抽取"地点+日期+描述"，和上面第5条"小红书解析"是同一类技术问题（自然语言地点抽取），成本和风险叠加，不建议现在做 | LLM API |

**如果以后真的要做第1、2条**，记得把下面两个从pitravel真实踩坑里学到的验收标准写进需求（成本为0，但容易漏）：
- **必须过滤"已关闭/暂停营业"的地点**（8.4节实测：pitravel的AI生成结果里出现了4个明确标注停业却仍被排进行程的地点，数据字段是对的但生成逻辑没用上）。
- **候选推荐池要排除已经加入本行程的地点**（8.5节实测：pitravel把已用过的"老门东"还留在待选池里）。

## 5. 已确认"应避免"的坑（QA/设计守则，成本=0）

这些不是"要新增的功能"，是从pitravel的真实缺陷里学到的、旅记应该主动避免重复犯的错误，建议整理进日常开发的检查清单：

- **坚持免登录可用**（4.1节）：旅记本地优先架构已经是核心差异化优势，不要为了运营/统计需求提前收紧本地免登录能力。
- **移动端网页体验要和桌面端对等**（4.3节）：不要学pitravel那样刻意阉割移动网页体验逼用户下载App，持续用真机验证PWA体验对等性。
- **分享面板不能静默改变可见性**（第2节第14条已列，此处不重复）。
- **AI/推荐类功能一旦做，必须主动过滤失效数据、去重候选池**（第4节末尾两条已列）。

## 6. 什么时候该重新评估付费档？（触发条件，供未来判断参考）

出现以下信号中的多个时，可以回来看第4节，评估要不要启动某一项付费功能：

- 已经有一批**真实使用、真实出行**的家庭（不是测试账号），而不只是招募阶段的体验用户。
- "旅记"开始有除人情/爱心之外的真实收入来源（哪怕很少，比如小额订阅、赞赏），能大致覆盖预估的月度API账单。
- 第2节的免费档功能已经基本上线，并收集过至少一轮真实用户反馈。
- 某个🔴功能被**同一批**用户反复主动提及，或能明确指向"没有这个功能所以流失/不推荐给朋友"。
